# 0.4.0 — proteção dos dados locais

Primeira implementação: **0.4.0-alpha.1**, na branch `protecao-dados/0.4.0`. Esta prévia implementa a base de proteção e recuperação. Login, revisões/SRS e a UI de estudos existente continuam com o comportamento anterior; as correções de revisão e a retirada do login pertencem às próximas fases.

## O que foi implementado

- Preflight de integridade, chaves estrangeiras, schema completo, histórico SQLx e compatibilidade do leitor antes de abrir o banco para estudos.
- Reconhecimento de bancos vazios, históricos válidos parciais e baselines legados que correspondam exatamente às migrations conhecidas.
- Registro auditável da equivalência dos checksums históricos LF/CRLF. As migrations 01–03 não foram alteradas. Não há bypass de checksum desconhecido.
- Migration 04 com registro de compatibilidade e auditoria. A versão do schema continua sendo controlada por `_sqlx_migrations`; a geração do leitor é uma proteção adicional, não um contador alternativo de migrations.
- Backup automático verificado antes de atualizar um banco existente e antes de restaurar um banco disponível. Falha no backup impede a transformação.
- Backup manual do SQLite e das imagens gerenciadas, incluindo alterações já confirmadas em WAL. Manifesto com hashes SHA-256, inventário, contagem de registros, schema, versão do aplicativo e diretório de origem.
- Verificação dos arquivos, banco e contagens antes da restauração. Imagens referenciadas ausentes ou externas à pasta gerenciada impedem a criação de uma cópia incompleta.
- Restauração com preparação separada, retenção dos arquivos anteriores e intenção persistente. Na próxima abertura, uma substituição interrompida é revertida antes de liberar o banco.
- Exclusão entre instâncias que usam esta implementação e trava de manutenção: comandos aguardam o backup e não acessam um pool encerrado após restauração.
- Tela de recuperação antes do login e acesso a “Dados e backups” durante o uso normal. Restaurar exige selecionar uma cópia e digitar RESTAURAR; após a operação, é necessário fechar e reabrir o aplicativo.
- Sincronização/verificação de versão em package.json, package-lock.json, Cargo.toml, Cargo.lock e tauri.conf.json; verificação de tag em CI e classificação de pre-release na publicação.
- CI para frontend e testes de armazenamento em Windows/Linux. A execução dos jobs remotos precisa ser acompanhada; a presença do workflow não comprova seu sucesso.

## Estrutura local

Dentro do `app_data_dir` resolvido pelo Tauri, mantendo o identificador `com.vinicius.revisum`:

```text
revisum.db
revisum.lock                    # arquivo de coordenação; não excluir enquanto o app estiver aberto
images/                         # imagens gerenciadas
backups/<UUID>/
  revisum.db
  images/
  manifest.json
recovery/<UUID>/
  candidate/                    # preparação ou arquivos da substituição revertida
  previous/                     # originais preservados
restore-intent.json             # existe somente durante uma substituição não finalizada
```

Pastas `.incomplete-<UUID>` são tentativas de backup não concluídas e não aparecem como cópias restauráveis. Manifestos ilegíveis são ignorados na listagem; um manifesto legível ainda precisa passar pela verificação completa ao restaurar. Nenhuma cópia é excluída automaticamente nesta prévia.

## Limites desta prévia

- O backup inclui banco e imagens; `store.json` contém o cache de login atual e não é restaurado. Ajustes da autenticação continuam a cargo da fase 0.5.0.
- A restauração automática aceita cópias do mesmo diretório de dados. Migração para outra máquina/pasta exige conversão dos caminhos absolutos das imagens e ainda não está implementada. A cópia pode ser guardada em outro disco e depois devolvida ao diretório backups de origem.
- Fechar versões antigas do Revisum e outros programas que abram o banco antes de iniciar. A trava de processo é cooperativa entre versões que a implementam; não limita ferramentas SQLite externas nem versões antigas.
- Os testes de interrupção cobrem etapas de substituição e repetição da recuperação. Não constituem homologação de perda abrupta de energia, falha física de disco ou de todos os sistemas de arquivos.
- O aplicativo não instala atualizações automaticamente nesta fase. Assinaturas do updater, feed e publicação de atualizações pertencem à 0.6.0.
- Não executar uma versão antiga sobre o banco atualizado: ela pode rejeitar o histórico novo. Retorno de versão exige um binário compatível e a cópia anterior, sem down migration automática.
- O desenvolvimento e os testes desta entrega não iniciam o aplicativo sobre o banco pessoal. A inspeção visual nativa e os instaladores por arquitetura são validações distintas dos testes automatizados.

## Verificação de desenvolvimento

Requisitos: Node >=22.12.0; CI fixada em 22.21.0; Rust 1.93.0 com rustfmt. Os comandos de teste usam fixtures sintéticas em diretórios temporários.

```text
npm ci
npm run version:check
npm test
npm run build
cargo test --manifest-path src-tauri/Cargo.toml --lib --locked
```

Para alterar a versão de uma entrega, atualizar package.json e executar `npm run version:sync`. `sversion.py` permanece como entrada de compatibilidade que chama o mesmo sincronizador Node. O sincronizador nunca lê ou reescreve migrations.

Ao adicionar uma migration, criar um arquivo novo e registrá-lo em `src-tauri/src/db/preflight.rs` na lista SCRIPTS. A fonte embarcada normaliza apenas LF/CRLF; o teste do registro de migrations exige que todos os arquivos estejam incluídos. Atualizar os critérios de schema e de compatibilidade quando houver mudança de geração; não apenas aumentar o número do aplicativo.

## Roteiro de aceitação antes de promover a estável

Validação local desta prévia em 15/10/2026: `npm ci` reproduzível, verificação dos cinco manifests, 19 testes Rust aprovados, 7 testes de interface aprovados, build web aprovado e executável Windows debug compilado com `npm run tauri -- build --debug --no-bundle -- --locked --offline`. O executável não foi iniciado. Os testes de UI usam IPC simulado; a tentativa de inspeção pelo navegador integrado não conseguiu conectar, portanto não conta como validação visual. CI remota, inspeção nativa e instaladores precisam de confirmação independente.

1. Usar um diretório de dados de teste separado, com cópia sintética ou autorizada; não trocar arquivos pessoais para simular falhas.
2. Abrir banco vazio e cópias v0.3.0 LF/CRLF. Conferir estudos, histórico e backup pré-migração; reabrir sem repetir a migração ou criar backups extras desnecessários.
3. Criar backup com imagens, fazer alterações, selecionar a cópia anterior, confirmar e reabrir. Conferir dados e imagens restaurados, além da retenção dos originais.
4. Abrir um banco desconhecido, corrompido ou de geração futura: a tela de recuperação deve aparecer antes do login, sem permitir estudos ou recriação silenciosa.
5. Adulterar um arquivo de uma cópia de teste: a restauração deve ser recusada antes de fechar o banco disponível.
6. Exercitar falta de permissão/espaço e encerramento forçado numa máquina de teste. Preservar os arquivos de recuperação; não removê-los para tentar “destravar”.
7. Conferir navegação por teclado, confirmação, foco, tema e tamanho de janela na WebView nativa.
8. Validar build/instalador nas arquiteturas publicadas e acompanhar CI Windows/Linux antes de promover a 0.4.0 estável. Não criar tag de release para apenas disparar testes.

O fluxo permanece `protecao-dados/0.4.0` → `dev` → `main`, com promoção após validação da entrega correspondente. A prévia alpha não representa a homologação de todos os instaladores ou da versão estável.
